# Agent 工具工作区 Review 与功能改进建议

- 日期：2026-11-15
- 范围：Agent Trace、Agent Stats、Agent Journal、Agent Knowledge
- 目标：追踪不同 agent 的使用情况与 token 消耗，支持定期复盘、经验沉淀和后续复用。
- 审查方式：阅读文档、核心源码与测试；运行现有测试和纯合成验证。未读取个人真实会话数据库、日报或凭证，未修改业务代码。
- 本文记录审查时的状态；源码链接行号可能随后续修改变化。

## 1. 总体判断

**方向正确，不建议推翻重做。最值得补的不是更多图表，而是这条闭环：**

> 哪个 agent → 为哪个任务 → 花了多少 → 结果怎样 → 得到什么经验 → 下次是否用上。

当前四个模块的职责划分合理：

| 模块 | 已有能力 | 主要待补环节 |
| --- | --- | --- |
| Agent Trace | Codex、pi、dsh 日志采集，统一事件归档，metadata/content 视图，删除标记 | 修订协议与消费方一致性、请求级覆盖信息、agent 身份维度 |
| Agent Stats | token/缓存/费用统计、父子会话、轮次和执行正文下钻 | 请求级完整性、任务级归因、端到端健康、不同 agent 对比 |
| Agent Journal | 确定性投影、云模型 map/reduce 日报、定时安装器 | 漏日补跑、旧日产物更新、总预算执行、逐条证据、周复盘 |
| Agent Knowledge | 本地知识检索、来源核验、归档证据读取 | 生成内容标记、经验候选审批、使用反馈和撤回闭环 |

短板主要在**统计可信度、任务归因和经验复用**，不是缺少采集入口。

已有设计应保留：未知值不补零；API 等价估算不冒充账单；父子关系只依赖明确身份；fork 与委派区别处理；执行证据不自动晋升为确认知识。

## 2. 优先修复的可信度问题

以下为现有实现问题或已知集成缺口，不是单纯新增功能建议。

### 2.1 请求级缺失可能被轮次级覆盖掩盖

**优先级：P1；验证方式：源码审查与纯内存合成验证。**

发现两种情况：

1. 同一轮两次请求，仅一次有 usage，仍可能显示该轮 token 覆盖完整。
2. Pi 同轮两次请求，仅一次记录费用，会把部分费用作为整轮费用。

合成结果：

- DSH 同轮两条 assistant 记录，仅一条携带 110 token 的 usage；Stats 返回 token_total=110、覆盖 1/1 轮，且没有缺失提醒。
- Pi 两次请求合计 220 token，第一条 cost_usd=0.01、第二条缺失；Stats 仍返回整轮费用 0.01，cost_samples=1。

影响：容易把“漏了数据”误认为“这个 agent 更省”，不适合直接用来比较效率。

建议：

- 保留可验证的请求身份和 usage/cost 是否存在的信息。
- 分开完整总量、已知小计和未知值。
- 展示请求级覆盖；来源无法可靠提供请求总数时保持未知，不按消息数猜测。
- 一轮部分请求有费用，不代表整轮费用完整。

依据：[用量聚合](<agent-stats/agent_stats/core.py#L17-L20>)、[覆盖统计](<agent-stats/agent_stats/core.py#L244-L260>)、[费用累加](<agent-stats/agent_stats/codex.py#L290-L297>)、[费用判断](<agent-stats/agent_stats/pricing.py#L43-L52>)。

### 2.2 上游事件修订与下游增量消费不兼容

**优先级：P1；验证方式：源码审查与纯内存合成验证。**

Trace 支持同一 event_id 的源记录变化后删除旧行并重新插入，获得新序号；Stats 对已经接收的同一 event_id 只允许新增，遇到新序号的修订会发生唯一键冲突。follow 将其归类为永久错误并退出。

合成结果：先消费 seq 1–5，再消费相同 event_id 的修订事件 seq 6，报 `conflicting archive event identity or sequence`，游标停留在 5。

建议：

- 明确事件 revision、替换和撤回语义，统一生产者与消费者契约。
- 修订应用、统计投影重建和游标提交保持事务一致。
- 增加“消费后源重写”“winning rollout 替换”“旧事件移除”的跨项目集成测试。
- 不应只验证 Trace 自身能成功处理重写。

依据：[Trace 修订](<agent-trace/src/store.ts#L218-L230>)、[Trace 重写测试](<agent-trace/tests/collector.test.ts#L203-L217>)、[Stats 导入](<agent-stats/agent_stats/archive.py#L246-L287>)、[follow 错误处理](<agent-stats/agent_stats/follow.py#L451-L453>)。

### 2.3 日报常规运行没有自动补漏日和更新旧日

**优先级：P1；验证方式：源码审查。**

常规 `run` 只计算 D-1，并调用一次日报生成。`maxDaysPerRun` 已配置，但没有用于遍历待处理日期。旧日被删除标记置为 stale 后，常规运行也不会主动重算它。

影响：断机后可能持续缺日报；迟到事件和删除无法自动更新更早的 Markdown。未来接入 Knowledge 后，未更新的旧文件也可能继续被检索。

建议：

- 建立待处理日期队列，涵盖漏日、迟到输入和 stale 日。
- 落实每次最大处理天数，并区分正常补日与显式历史回补策略。
- 删除发生后先使受影响产物不可作为有效知识使用，再重算和同步索引。
- 增加“D1 日报 → D3 删除或迟到事件 → 常规 run → D1 产物更新”的测试。

依据：[日报调度](<agent-journal/src/cli.ts#L123-L133>)、[单日报生成与跳过条件](<agent-journal/src/dream.ts#L80-L136>)。

### 2.4 日报每日输出预算未执行，失败花费记录不完整

**优先级：P1；验证方式：源码审查与 fake provider 合成验证。**

`maxOutputTokensPerDay` 已解析，但 map/reduce 每次调用只使用单次 `model.maxOutputTokens`，没有执行累计输出预算。失败运行仅保存错误，没有完整保留此前成功调用的 usage。

合成结果：每日输出预算为 100，两次调用各输出 80，累计 160，流程仍成功。

建议：

- 每次调用前检查剩余预算，并限制单次最大输出。
- 逐调用持久化 usage，失败和重试也保留已发生的消耗；供应商未返回 usage 时标记未知。
- 增加 map 缓存和断点恢复，避免 reduce 失败导致全部 map 重跑。
- 区分原 agent 的实际用量、投影字符估算和复盘模型自身用量。

依据：[模型调用](<agent-journal/src/model.ts#L327-L355>)、[失败记录](<agent-journal/src/dream.ts#L149-L154>)。

### 2.5 日报证据与生成内容标记尚未贯通

**优先级：P1；性质：实现缺口与已公开标注的集成前置条件。**

日报顶层亮点、决策、阻塞和下一步目前是字符串列表，并未强制逐条绑定证据。会话摘要虽有 session_key 校验，渲染主要输出文字 session_id，不等于可直接定位到具体事件。

Knowledge 的记录类型和导入流程固定 `generated: false`。现阶段若把模型日报作为普通 source 目录接入，会失去“二手生成摘要”与直接来源知识的区别。

建议：

- 每条结论采用结构化表示：`claim`、`evidence_refs`、`status`。
- 证据保留 archive_id、event_id、session_key，并提供稳定的读取入口。
- 在 source、record、存储和检索返回中贯通 generated 标记、生成模型与 prompt 版本。
- 候选经验未经确认，不进入确认事实的默认检索范围。
- 防止“日报 → 知识 → 下次日报”循环自证。

依据：[日报结构](<agent-journal/src/model.ts#L26-L35>)、[顶层输出校验](<agent-journal/src/model.ts#L286-L295>)、[会话引用渲染](<agent-journal/src/render.ts#L168-L179>)、[知识导入](<agent-knowledge/src/application/index.ts#L85-L93>)。

## 3. 最值得新增的五项功能

| 优先级 | 功能 | 用户价值 |
| --- | --- | --- |
| P1 | 任务级成本账本 | 把多个会话、不同宿主和子 agent 关联到一个任务，回答“完成这件事总共花了多少” |
| P1 | Agent 对比视图 | 区分宿主、角色/preset、provider、model，展示自身与含后代消耗 |
| P1 | 可行动的周复盘 | 识别高消耗任务、反复返工和阻塞，形成下周可验证的改进 |
| P1 | 经验候选收件箱 | 自动提出经验，由人确认、修改或驳回，再进入复用流程 |
| P2 | 采集健康与覆盖面板 | 展示最后采集时间、同步延迟、错误、未归属项目和用量缺失，避免误读数据 |

### 3.1 首推：任务级成本账本

目前主要分析单位是会话和轮次，但真实工作常常是：

> Codex 探索 → dsh 实现 → 子 agent review → 新会话修问题。

这些活动应该可以归到同一个任务，而不只是分别显示在会话列表中。

建议任务卡包含：

- 目标、项目、任务类型与标签；
- 关联会话、参与 agents、模型与委派关系；
- 输入、缓存读取、缓存写入、输出 token；
- 已记录费用与 API 等价估算，分别展示来源与完整性；
- 任务结果：完成、部分完成、放弃、待验证；
- 验证证据和人工评价；
- 关联复盘、候选经验与已确认经验。

**第一版允许手工归组和标记结果，不必立即使用模型自动判断。** 工具执行成功不等于任务完成，agent 自称完成也不等于用户验收。

有结果维度后，才适合比较同类任务中哪个 agent 更合适，而不是简单比较谁花得少。

### 3.2 Agent 身份和比较口径

不要把 agent 等同于模型，也不要把一个会话等同于一个完整任务。

建议分开保留：

- runtime：Codex、pi、dsh；
- instance：设备或运行环境；
- agent preset/角色：实现、研究、review 等，仅使用明确来源或人工标注；
- provider 与 model；
- task、session、turn、request 身份；
- 可验证的父子或委派关系。

展示上分开“自身消耗”和“含后代消耗”，避免重复汇总。来源没有父轮次身份时继续显示未知，不按时间猜测。不同任务难度和类型应分组比较，不做未经控制的全局效率排行榜。

### 3.3 端到端健康与覆盖面板

建议串联显示：

> 来源发现/导入/未匹配/待完成 → Trace 最近成功与高水位 → 消费方游标与延迟 → token/费用覆盖 → 日报状态。

“服务在线”“请求成功”“数据已追平”“业务覆盖完整”是不同状态。空页请求成功，不代表上游采集健康。

周报或月报应记录生成时的数据范围、覆盖率和截止游标；采集停滞或覆盖下降时，将报告标为不完整，而不是照常得出“本周成本下降”的结论。

## 4. 复盘与经验沉淀设计

### 4.1 每日：短，不追求流水账

固定输出五项：

1. 完成了什么；
2. 未完成与阻塞；
3. 消耗最高的任务；
4. 候选经验；
5. 下一步。

统计数字由确定性代码提供，模型负责组织叙述；每条重要结论保留证据入口。

### 4.2 每周：看变化，形成行动

重点回答：

- 消耗增加来自任务变多、任务更难，还是返工更多？
- 哪些任务值得换模型、调整拆分方式或提前补充上下文？
- 上周提出的改进是否执行？
- 哪些经验被复用，实际是否有效？

每次周复盘最终落到少量行动项，带验证标准，并在下周回看。

#### 先统一统计时间口径

Stats 目前按 UTC 的轮次开始时间分日；Journal 按本地时区的事件发生时间分日。跨午夜任务可能对不上，不能把两边同名日期直接当成相同统计范围。

建议显式约定：时区、半开日窗口、统计单位、跨日用量归属、迟到数据修订。对累计计数按来源语义处理，不能直接把日末会话累计值当作当日消耗。

依据：[Stats 时间口径](<agent-stats/agent_stats/core.py#L229-L260>)、[Journal 日窗口](<agent-journal/src/dream.ts#L80-L85>)。

### 4.3 长期：经验卡，而不是日报堆积

经验卡建议包含：

> 适用场景 → 建议做法 → 原因 → 来源证据 → 例外条件 → 验证状态。

生命周期：

> 候选 → 人工确认或驳回 → 实际使用 → 有效/无效/未知反馈 → 修订或撤回。

关键区别：

- 被检索到，不等于被使用；
- 被使用，不等于有效；
- 多次模型重复同一说法，不等于得到独立证据；
- 来源被删除或结论被推翻后，衍生经验需要失效或重新验证。

先实现人工批准的最小闭环，再考虑自动晋升和跨天整合。

## 5. 建议实施顺序与验收目标

| 阶段 | 交付 | 建议验收目标 |
| --- | --- | --- |
| 1. 统计与同步可信 | 请求级覆盖、修订协议、日口径、日报预算与补漏 | 缺失不表现为完整；源修订后消费不中断；跨日样例可解释；预算和漏日策略有合成测试 |
| 2. 任务归因 | 任务卡、会话归组、结果标注、agent 身份 | 一个跨宿主/子代理任务可查看去重后的已知消耗、未知部分与结果证据 |
| 3. 周复盘 | 任务变化、消耗集中项、返工与行动项 | 每条关键结论可回查；上周行动可在本周验证；不完整数据有明确提醒 |
| 4. 经验确认 | generated 标记、候选收件箱、人工审批、证据引用 | 未确认摘要不冒充事实；经验可修正、驳回、撤回 |
| 5. 复用反馈 | 检索、使用关联、有效性反馈 | 新任务能找到适用经验，并记录是否使用、是否有效及验证依据 |

暂不优先：更多适配器、复杂向量库、全自动经验晋升、未经任务分组的 agent 排行榜。先用现有三个来源形成可靠的小闭环。

## 6. 补充可靠性发现

### Follow 租约续租不应依赖空闲等待

Stats follow 租约为 30 秒，续租集中在等待逻辑。连续追赶分页时不进入等待，可能在活进程工作期间过期。假时钟合成验证中，第二 owner 在租约过期后获得租约，旧 worker 随后仍成功写入下一页。

建议独立续租，并在应用页面的事务中校验 owner 与有效期；补充追赶超过 TTL、慢请求和旧 worker 被抢占后禁止写入的测试。

此项属于现有实现修复，宜并入第一阶段，而不是仅用健康面板掩盖。

依据：[follow 主循环](<agent-stats/agent_stats/follow.py#L491-L522>)、[follow 实现](<agent-stats/agent_stats/follow.py>)。

**最终建议：先让数据可信，再让消耗归因到任务，最后让复盘产物成为可核验、可撤回、能反馈效果的经验。**
