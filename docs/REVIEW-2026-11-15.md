# Agent Observatory Review：从使用追踪到复盘与经验复用

日期：2026-11-15（Asia/Shanghai）  
目标：追踪 agent 的使用情况，理解 token 消耗，定期复盘，并沉淀可复用经验。

## 1. 结论先行

**方向是对的，模块基础也不错；但当前更像四个有用工具组成的基础设施，还不是一个可信、自动运转的个人复盘系统。**

不建议推翻重写，也不建议此时优先加向量数据库、更多图表或更多宿主适配器。最值得投入的是：

1. **先让数字可信**：请求级用量与费用缺失不能被聚合掩盖，事件修订要能传到下游。
2. **再让运行可靠**：断机补日、迟到重算、删除传播、生成物冲突保护必须闭环。
3. **围绕任务而非会话复盘**：把目标、主子 agent、成本、结果和证据关联起来。
4. **经验先成为候选，再经确认复用**：生成摘要不等于事实，能搜索不等于已沉淀有效知识。

对你的需求，最小可用闭环应是：

```text
明确采集范围 → 可靠用量账本 → 任务与结果关联
             → 每日记录 → 每周复盘 → 人工确认经验
             → 下次任务检索使用 → 有效性反馈与撤回
```

目前前半段已有较多实现，后半段主要还是设计方向。

## 3. 已有基础：哪些值得保留

| 目标 | 当前能力 | 判断 |
| --- | --- | --- |
| 追踪执行 | Trace 支持 Codex / pi / dsh，metadata/content 分离，有游标、归档、删除标记 | 是可靠性工作的好起点，但源日志不是完整账单 |
| 理解消耗 | Stats 有用量、缓存、费用估算、会话/轮次与父子归属 | 对未知值和重叠已有保护，但缺少请求级覆盖语义 |
| 每日复盘 | Journal 有确定性日报、可选 map/reduce 摘要、输入哈希与产物版本 | 可手动使用，不宜假定已具备无人值守补漏能力 |
| 知识复用 | Knowledge 有文件索引、带来源读取、归档证据检索、MCP | 是检索底座，不是已完成的自动经验管理系统 |

尤其应保留：

- 四模块可独立使用、Trace 可选的边界，不引入强制总控服务。见[架构说明](<ARCHITECTURE.md#L15-L46>)。
- Stats 不把费用估算称作账单，不重复累加缓存输入/推理输出，父子口径不确定时会阻止汇总。见[费用口径](<../packages/agent-stats/agent_stats/pricing.py#L6-L18>)、[父子汇总保护](<../packages/agent-stats/agent_stats/core.py#L220-L251>)。
- Knowledge 区分归档证据与活跃知识，不能笼统说它已经把所有对话自动当事实。见[模块边界](<../packages/agent-knowledge/README.md#L51-L62>)。
- 已有大量合成测试、输入校验、安装器显式授权和独立发行验证。问题是需要补业务故障场景，而不是没有工程基础。

## 4. 具体问题与修复建议

### R1 · P1 · 部分请求费用会被当成完整轮次费用

**证据**：[请求费用累加](<../packages/agent-stats/agent_stats/codex.py#L290-L297>)只累计存在的 `cost_usd`；[估算入口](<../packages/agent-stats/agent_stats/pricing.py#L43-L52>)只要有 recorded cost 就直接作为整轮费用；[聚合](<../packages/agent-stats/agent_stats/pricing.py#L84-L100>)判断的是多少轮有费用，不是多少请求有费用。

**影响**：一轮内两次请求，只有一次记录 $0.02，另一笔未知，结果仍可能把 $0.02 显示为完整轮次/总费用，而不是已知小计。这会系统性低估成本，直接影响复盘判断。

**建议**：保留请求级成本事实及完整性；分别输出 `known_cost`、`complete_cost`、已观测请求数、有费用请求数。来源无法证明总请求数时，覆盖率也必须是未知，不能拿消息数代替。

**验收**：同轮两请求、一个成本未知；显式零成本；全未知；混合 provider；重放不重复。部分费用只能出现在小计，完整费用应为 null。

### R2 · P1 · 合成累计 usage 会掩盖逐请求字段缺失

**证据**：DSH 与 pi 对已有字段维护累计值，后续请求缺字段时保留此前累计字段，见[DSH 累计](<../packages/agent-trace/src/dsh.ts#L354-L363>)、[pi 累计](<../packages/agent-trace/src/pi.ts#L227-L237>)；Stats 根据累计快照差分，见[差分与字段观测](<../packages/agent-stats/agent_stats/codex.py#L240-L245>)、[字段累加](<../packages/agent-stats/agent_stats/codex.py#L303-L321>)。

**影响**：第一次缓存输入 20，第二次缓存字段缺失，累计仍为 20，差分得到 0；“未知”被伪装成“已知零新增”。缓存比例与按分类估算的费用可能显得完整。

**建议**：区分源生累计计数与适配器合成累计计数。合成时保留每次请求字段 presence/quality；缺失不能用上次累计推导成零。既有原生累计快照的有效差分逻辑应单独保留。

**验收**：同轮、跨轮分别覆盖字段缺失、显式 0、缺失后恢复、计数重置、fork 基线。缺失不能被后续聚合抹掉。

### R3 · P1 · 源事件修订与 Journal 增量消费契约不一致

**证据**：Trace 对变化事件删除旧行再插入新行，未变化事件保持序号，见[源修订处理](<../packages/agent-trace/src/store.ts#L208-L230>)；Journal 已见过同 event_id 后，只接受同序号同 data，否则永久错误，见[导入冲突判断](<../packages/agent-journal/src/store.ts#L299-L315>)。

**影响**：已消费事件随后在源端被改写，同 ID 获得新序号时，Journal 会拒绝这页；若源事件直接被移除，没有逐事件撤回通知，下游还可能保留旧内容。只测试 Trace 自身的重写正确是不够的。

**建议**：先定义版本化 change feed：稳定逻辑 ID、revision、upsert/retract、替代关系、墓碑；不要简单放宽消费者去重。投影变更与游标必须同事务，并明确旧消费者迁移策略。

**验收**：先消费，再改写/移除源记录，再消费；最终投影与完整重建一致。覆盖重放、回滚、游标恢复。Stats、Knowledge 也应纳入跨模块矩阵，本节不声称已逐个复现它们所有表现。

### R4 · P1 · 日报没有补跑队列，删除未清理历史产物

**证据**：常规 `run` 只生成指定日或昨天，见[命令调度](<../packages/agent-journal/src/cli.ts#L135-L145>)；删除事件仅清理 SQLite 并将相关日标记 stale，见[删除处理](<../packages/agent-journal/src/store.ts#L280-L294>)。

**影响**：停机几天后不会自动补齐；历史日期 stale 不会被常规运行主动重算。源会话删除后，已生成日报中的敏感内容仍可能留在磁盘并被文件索引继续使用。不能将“源删除成功”等同于“所有衍生物删除成功”。

**建议**：持久化 dirty-day 队列，覆盖漏日、迟到、修订和删除；按配置上限处理，失败可重试。删除触发立即隔离受影响的受管产物，再重建和同步索引。人工编辑部分不要未经确认直接删除。

**验收**：D1 出日报，D3 删除/新增迟到事件，常规 `run` 能处理 D1；断机三天按上限补齐；衍生物失效状态可见；删除内容不能继续被检索为有效知识。

### R5 · P1 · 自动重生成可能覆盖用户在日报里的手工复盘

**证据**：[跳过条件](<../packages/agent-journal/src/dream.ts#L110-L115>)要求文件哈希未变；用户修改后不满足条件，随后仍[覆盖输出](<../packages/agent-journal/src/dream.ts#L161-L163>)；底层写入用 rename 替换目标，见[写文件实现](<../packages/agent-journal/src/dream.ts#L49-L54>)。

**影响**：即使未传 `--force`，用户补充的判断、行动项和经验也可能在下一次生成时丢失。这对“沉淀总结”尤其危险。

**建议**：生成区与人工区分离，或生成物不可变版本化；哈希冲突默认停止覆盖、输出新版本并提示。`--force` 的覆盖语义明确化，保留恢复路径。

**验收**：生成后手改，再普通运行，手改必须保留；源变化时也不能悄悄覆盖。测试进程中断、写入失败与版本恢复。

### R6 · P1 · 总结模型的预算和失败消耗不是完整账本

**证据**：[map/reduce 调用](<../packages/agent-journal/src/model.ts#L327-L364>)逐次使用模型的单调用输出上限，未在这里扣减日累计输出余额；成功调用的 usage 仅在内存累计。[失败处理](<../packages/agent-journal/src/dream.ts#L142-L155>)写入错误信息，不持久化已完成调用的 usage。

**影响**：map 已产生消耗、reduce 失败时，成本记录不完整；重跑会重新调用 map。每日预算不能只靠选择输入会话与单次 max tokens 保证。

**建议**：逐调用写 ledger，保存请求、模型、阶段、状态、usage/unknown；调用前预留预算，完成后结算。map 缓存键包含输入哈希、模型/供应商配置和 prompt 版本。未知 usage 不按零处理；真实供应商未报告的费用不能承诺可精确恢复。

**验收**：成功两次后失败仍保留已发生用量；reduce 重试复用未变 map；多次手动重跑共享同日预算；模型调用成本与被观察 agent 的工作成本分开展示。

### R7 · P1 · 缺时间事件没有进入日报覆盖统计

**证据**：[按日查询](<../packages/agent-journal/src/store.ts#L326-L329>)排除了 `occurred_at IS NULL`；但[投影覆盖](<../packages/agent-journal/src/projection.ts#L295-L313>)随后才统计缺失时间。

**影响**：正常 dream 链路里 `occurred_at_missing` 看起来为零，却不能证明源数据没有缺时间；这些记录也没有进入叙述。采集成功与内容覆盖完整是两件事。

**建议**：单列未归属事件数，以 observed_at 统计“何时看到”，但不能冒充实际发生日；日报展示未归属、截断、外置正文未读、迟到排除和会话丢弃数量。

**验收**：有一条 occurred_at=null 的事件时，全局/日报旁的覆盖诊断能够发现；它不会被静默认作当天真实活动。

### R8 · P2 · Stats 与 Journal 的日期和 token 含义不同，缺少统一复盘接口

**证据**：Stats 按 UTC 轮次开始日期分桶，见[分桶](<../packages/agent-stats/agent_stats/core.py#L230-L232>)及[时间口径](<../packages/agent-stats/agent_stats/core.py#L257-L260>)；Journal 用配置时区的事件日窗口，见[日期投影入口](<../packages/agent-journal/src/dream.ts#L80-L98>)。Journal 的 projected_tokens 是[文本字符估算](<../packages/agent-journal/src/projection.ts#L109-L112>)，不是实际 agent 消耗。

**影响**：上海 11 月 15 日 00:30 对应 UTC 11 月 14 日 16:30，两份“当天”报告会对不上；跨午夜轮次归属也不同。不能直接将日报投影 token 与 Stats usage 相加或对账。现有命名有区分，这里主要是跨模块产品缺口。

**建议**：统一报告参数 `timezone + [start,end) + allocation_basis`，同时保留原时间；用量以请求发生时计日，无法细分则明确按轮归属。日报引用 Stats 的可靠聚合，不重新实现一套含义不同的用量统计。

**验收**：跨午夜、跨日长会话、夏令时、缺失时间都有可解释结果；UI、导出、日报统一标注时区与归属依据。

### R9 · P1（自动入库前）· 摘要可追到会话，但结论还没有逐条证据与审批状态

**证据**：[模型输出验证](<../packages/agent-journal/src/model.ts#L252-L296>)校验 project/session 身份，但 highlights、decisions、blockers 等仍是字符串数组；Knowledge 明确[自动提取与晋升未实现](<../packages/agent-knowledge/README.md#L7-L9>)，且 [generated 标记仍待实现](<../packages/agent-knowledge/README.md#L62-L70>)。

**影响**：“agent 说已完成”可能被总结为事实；若索引生成日报而不保留生成属性，后续 agent 可能引用摘要为摘要背书。会话级关联不能证明每条具体结论。

**建议**：每条 claim 附 evidence refs、来源版本、支持/反对证据、生成模型与 prompt 版本，区分 observation / inference / decision。经验走 candidate → accepted/rejected → superseded/revoked；未经确认内容只能作为明确标注的候选，不进入默认已确认知识范围。

**验收**：无证据结论不会自动晋升；能从经验追到具体事件/文件版本；证据删除、修订触发失效或复核；人工确认与驳回可审计。

## 5. 面向你的目标，产品层最缺什么

### 5.1 一个轻量任务账本，而非再建一个总控平台

会话不是任务：一个任务可能跨天、跨宿主、包含多个子 agent；一个会话也可能切换目标。现在的会话/轮次统计适合看“发生了什么”，不够解释“为什么花这么多，值得吗”。

建议先手工关联，避免 LLM 自动猜测误归属：

| 对象 | 最小字段与约束 |
| --- | --- |
| Task | task_id、项目、目标、任务类型、关联会话/轮次、开始结束、结果、验收证据 |
| AgentRun | runtime、instance、role、provider、model、parent_run_id、关联依据 |
| UsageFact | 请求身份（来源有则保留）、各 token 字段及 presence、成本 basis、源事件/版本、重试关系 |
| ReviewItem | 结论、证据、行动项、负责人/复查日期、完成状态 |
| KnowledgeCandidate | 内容、适用条件、反例、来源版本、生成来源、审批与撤回状态 |

请求 ID 不可得时标 `granularity=turn/session`，不要伪造请求身份。root_task 的唯一调用去重总量、agent 自身用量和含后代用量分别显示；含后代总量不能再逐 agent 相加。

### 5.2 看板应该回答问题，而不是只展示数值

建议优先三个视图：

1. **消耗视图**：本周按项目/任务/模型的已知 token 与费用、变化量、最贵的 5 个任务、重试/失败的已知开销。旁边始终显示数据覆盖。
2. **运行健康视图**：来源发现/未匹配、最后采集成功、解析失败、消费游标延迟、待补日报、stale 产物。在线≠追平≠覆盖完整。
3. **复盘收件箱**：待确认结论、未完成行动项、待审核经验、已撤回经验。先形成可执行反馈，不必先实现复杂知识图谱。

不要用 token 少就判定 agent 好。比较至少控制任务类型、难度、结果与质量；先看“完成一个经验证任务的成本”，再比较模型或角色。

### 5.3 周复盘比更多自动摘要更有价值

建议周报固定回答：

- 这周目标是什么，哪些已验证完成，哪些只是 agent 声称完成？
- 消耗集中在哪些任务？相对上周变化能否用任务构成解释？
- 哪些开销来自返工、重试、上下文过长或重复派发？证据是什么？
- 哪 1–3 项流程改进值得尝试？下周怎么验证有效？
- 哪些经验值得确认入库，适用范围和反例是什么？

统计部分确定性生成；叙述部分模型可选；人工只需确认关键结论和行动项。自动化的目标是减少整理负担，不是代替事实核验。

## 6. 建议实施顺序与验收门槛

不估算未经排期的完成日期，以可交付结果推进：

| 阶段 | 优先工作 | 完成标准 |
| --- | --- | --- |
| A：可信数据 | R1/R2 请求字段覆盖；R3 修订/撤回协议；R7 缺时间诊断 | 多请求缺失、零值、修订、删除的端到端金样例通过；增量投影与重建一致 |
| B：可靠日报 | R4 补日/失效队列；R5 人工内容保护；R6 调用账本和预算 | 停机恢复不漏日、失败可重试、删除传播、手改不丢失、失败消耗可见 |
| C：可用复盘 | R8 时间口径；任务手工关联；周报与行动项；健康面板 | 一周数据可从任务结果追到成本与源证据；每条行动项有复查结果 |
| D：可信沉淀 | R9 claim/provenance/审批；经验反馈与撤回 | 相似任务能找到经确认经验；引用可核验；过期/被撤回内容不作为有效事实 |

保持模块独立：用小范围版本化契约和共享金样例协作，不建立跨语言万能 core。对普通个人用户可以提供一份配置向导/doctor/统一状态摘要，但它应是可选入口，不改变独立安装能力。

## 7. 运行与隐私：必须明确的边界

- **metadata 优先，正文按项目显式启用**。日志可能含提示、工具参数/结果和敏感路径；启发式脱敏不是无泄漏保证。见[正文安全边界](<../packages/agent-trace/src/content.ts#L7-L25>)。
- 配置模型总结意味着选定正文可能发送给 provider；上线前明确 endpoint、允许项目、脱敏策略和预算，不能只因为数据库在本机就认为数据不外发。
- 保留期覆盖 Trace 内容/外置 blob、消费者数据库、日报、知识索引和备份。删除必须有各层完成状态；离线消费者需要的墓碑不可提前 GC。备份若不能立即物理清除，应有过期与恢复时重放删除的政策。
- 固定范围试点优于一次性导入所有历史。先人工核对少量会话、跨日任务与父子 agent 样例，再扩大来源范围。
- 沿用现有回环服务、授权校验、独立状态目录与显式安装确认；本次不建议迁到云端集中存储。

## 8. 待单独验证，暂不作为本轮已确认缺陷

1. Stats follow 长时间追赶、慢请求与租约过期后的旧 owner 提交保护：见[既有待办](<../TODO.md#L28-L32>)，需要假时钟和双连接测试。
2. Journal 接受带偏移时间时，导入到 SQL 文本比较之间是否始终规范化为 UTC：需要从输入校验到落库的端到端验证，不仅测试日期工具。
3. 真实宿主更新后的格式兼容、日志缺失/损坏/重写频率，长期增长下查询延迟与磁盘占用。
4. 真实中文检索质量、外置正文检索覆盖、总结事实性，以及经验是否真的改善后续任务。
5. UI 视觉与交互验收、实际部署后的休眠唤醒/断网恢复、远端 CI。历史记录不能代替本仓库本轮验证。
